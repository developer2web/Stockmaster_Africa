# Nettoyage StockMaster — 9 septembre 2026

## Changements

- Catégories de produits retirées des menus, routes, formulaires, catalogues, ventes, rapports et permissions proposées. Recherche par nom/code-barres conservée. Les anciennes tables et migrations SQL restent en place pour conserver la compatibilité et les données historiques. Les RPC de création et de rapport reçoivent toujours `p_category_id: null`.
- Ventes : recherche par référence/client, panneau « Filtrer » replié, période avec calendriers, moyen de paiement et règlement séparés. « Reste à payer » inclut les paiements partiels. Les filtres s’appliquent sur le serveur avant pagination. Le total indique explicitement le nombre de ventes affichées ; les bénéfices restent indépendants de l’accès à l’historique.
- Notifications : expiration 48 heures après la création, lues ou non, dans l’application, le badge et le portail propriétaire. Le centre affiche les notifications datées ; les alertes d’état recalculées sans date ne sont plus dupliquées dans cet historique. Les informations de stock/dette restent disponibles sur leurs écrans métier.
- Suppression serveur des notifications expirées chaque minute ; les règles d’accès par destinataire sont conservées. Les ventes, paiements, factures, dettes et journaux de sécurité ne sont pas supprimés.

## Mise en service Supabase

Les modifications du serveur sont préparées localement. Elles ne sont pas déclarées déployées.

Appliquer dans cet ordre sur le projet Supabase utilisé par l’application, via les migrations habituelles ou le SQL Editor :

1. `supabase/migrations/202609090002_filtered_sales_history.sql`
2. `supabase/migrations/202609090003_notification_retention.sql`

La deuxième migration efface dès son application les notifications âgées d’au moins 48 heures, puis programme le nettoyage chaque minute. Elle utilise `pg_cron` et le schéma `private` déjà créés par la migration de notifications email du 25 août. Les notifications expirées sont immédiatement exclues des lectures par la règle RLS, même avant le passage du nettoyage.

Vérifier ensuite dans le SQL Editor :

```sql
select jobname, schedule, active
from cron.job
where jobname = 'stockmaster-notification-retention';

select count(*) as expired_notifications
from public.notifications
where created_at <= now() - interval '48 hours';
```

Le job doit être actif avec la fréquence `* * * * *`. Le compteur doit revenir à zéro après son passage. Redémarrer/recharger l’application après publication de sa nouvelle version. Sans la première migration, l’historique sans filtre reste accessible et l’utilisation des nouveaux filtres affiche un message de mise à jour serveur nécessaire.
