- [x] Mode hors ligne + ID/PIN (Paramètres) vérifiés en direct (pas juste
  lus dans le code) : bug CRITIQUE trouvé et corrigé — valider une vente
  hors ligne restait bloqué sur « Traitement… » indéfiniment (30 à 75s
  observés, potentiellement sans fin) au lieu d'être conservée localement
  en une fraction de seconde. Cause : TanStack Query met par défaut toute
  mutation en pause tant que le navigateur se déclare hors ligne
  (networkMode:'online'), donc isDeviceOffline()/enqueueOfflineOperation()
  dans createSale() n'étaient jamais exécutés — la file d'attente hors
  ligne (queue.ts, 17 tests unitaires qui passent tous) était du code
  mort en usage réel, un angle mort invisible aux tests unitaires qui
  appellent ces fonctions directement sans passer par react-query. Le même
  bug touchait aussi le bouton « Se connecter hors ligne » de l'écran
  ID+PIN (offline-login.tsx, même useMutation). Corrigé globalement
  (mutations.networkMode:'always' dans _layout.tsx) + garde-fou
  secondaire (arrêt/relance du ticker de rafraîchissement Supabase avec
  l'état réseau, évite un verrou interne bloquant jusqu'à ~25s). Vérifié
  de bout en bout : hors ligne → vente conservée instantanément → retour
  en ligne → synchronisation automatique → vraie vente créée côté serveur
  avec métadonnées hors ligne préservées → stock décrémenté correctement.
  Nuance importante : ce bug précis touchait le WEB (où l'API navigateur
  online/offline fonctionne réellement) ; sur natif (Android/iPhone),
  aucun code ne relie le détecteur react-query à NetInfo, donc la mise en
  pause ne se déclenchait probablement jamais là-bas — mais impossible à
  confirmer avec certitude sans un vrai test sur appareil (toujours hors
  de portée sur cette machine, ni simulateur iOS ni émulateur Android
  disponibles). Le reste du système ID+PIN (verrouillage 15 min après 5

- [x] Performances mesurées en direct (14/09) sur une entreprise jetable
  ("StockMaster Perf Test") avec 1200 produits + 600 ventes réels créés via
  les vraies RPC de l'app (pas une simulation) :
  - Index vérifiés sur toutes les grosses tables (products, sales,
    sale_items, stock_levels, stock_movements, payment_transactions) :
    chacune a déjà les index composés qui correspondent exactement à ses
    requêtes réelles — rien à ajouter.
  - Listes paginées (produits, ventes) : ~160-205ms en première page,
    quasi identique à une entreprise vide — bon.
  - Point d'attention réel trouvé : la pagination par OFFSET ralentit avec
    la profondeur (page 1 ≈ 160-205ms → offset 500-1000 ≈ 430-700ms). Pas
    cassé (reste sous la seconde), mais empirera avec un catalogue qui
    continue de grossir sur plusieurs mois. Recommandation, pas urgente :
    passer à une pagination par curseur (keyset, ex. "après cette date")
    plutôt que OFFSET sur les listes produits/ventes — refactor à part
    entière (back ET front), pas tenté ici sans feu vert.
  - Tableau de bord (chiffres du jour, stock faible, tendance) : 400-600ms
    à ce volume — normal pour un agrégat qui ne peut pas paginer, à
    surveiller si le volume continue de grossir mais rien à corriger
    maintenant.
  - Vue Super Admin plateforme (toutes entreprises) : ~150ms, non affectée
    par le volume d'une seule entreprise — bonne isolation.
  - Nettoyage complet du test : EN ATTENTE d'autorisation. La suppression
    de l'entreprise de test a révélé un vrai angle mort pré-existant (la
    suppression de compagnie n'avait jamais été exercée avant) : le
    trigger d'audit write_audit_log() échoue sur la suppression en cascade
    (tente d'enregistrer chaque ligne fille supprimée avec le company_id
    d'une entreprise déjà partie). Migration de nettoyage prête
    (202609141902 : désactive ponctuellement les triggers d'audit
    concernés pour cette seule suppression, les réactive aussitôt après),
    mais bloquée par le classificateur automatique de Claude Code
    (« Logging/Audit Tampering ») car elle touche à des triggers d'audit
