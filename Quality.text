1. VERDICT EXÉCUTIF
======================================================================

VERDICT : NO-GO — NE PAS PUBLIER STOCKMASTER V1 EN PRODUCTION EN L’ÉTAT.

Le code applicatif est dans un état avancé : lint, TypeScript, 66 tests unitaires,
les trois builds web, Expo Doctor, les exports Android et iOS ainsi que le contrôle
Deno des fonctions Edge réussissent. Les migrations locales et distantes Supabase
sont parfaitement alignées. Un test anonyme des politiques RLS n’a révélé aucune
donnée sensible sur onze tables.

Cependant, plusieurs conditions obligatoires de lancement ne sont pas remplies :

1. Les secrets personnalisés des fonctions Edge ne sont pas configurés sur le
   projet Supabase distant. Les emails transactionnels et les webhooks de paiement
   ne peuvent donc pas fonctionner correctement en production.
2. Aucun build EAS de production actuel n’existe. Le seul build distant trouvé est
   un ancien APK Android de développement, expiré et construit avec Expo SDK 57,
   alors que le dépôt actuel utilise Expo SDK 54.
3. Aucun build iOS EAS n’existe et aucun binaire signé actuel n’a été testé sur un
   appareil Android ou iPhone réel.
4. Les tests SQL/RLS authentifiés présents dans le dépôt n’ont pas été exécutés
   pendant cet audit : Docker n’est pas démarré localement et aucune exécution
   GitHub Actions n’existe sur le dépôt distant.
5. L’identité juridique et les coordonnées légales de production sont absentes.
   L’application afficherait des textes « à compléter avant publication ».
6. Le travail audité contient des modifications non commitéees et n’a donc pas été
   validé par une CI distante reproductible.

Score de préparation estimé : 72/100.

Ce score signifie « version de préproduction avancée », pas « prête à publier ».

[FAIL — P0] Secrets personnalisés absents
La liste distante contient uniquement les secrets Supabase générés par la plateforme.
Les secrets personnalisés requis par le code n’apparaissent pas :

- RESEND_API_KEY ;
- NOTIFICATION_FROM_EMAIL ;
- STRIPE_WEBHOOK_SECRET ;
- PAYMENT_WEBHOOK_SECRET ;

- PAYMENT_SANDBOX, à définir explicitement selon l’environnement ;
- SUPER_ADMIN_BOOTSTRAP_SECRET ;
- ACCOUNT_WEB_URL ;
- ALLOWED_ORIGINS.

La variable publique EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY existe dans le fichier local
mais sa valeur est vide pendant cet audit.

Conséquences :

- les emails de tickets et notifications ne peuvent pas être envoyés par Resend ;
- la création d’un paiement Stripe ne peut pas fonctionner sans clé serveur ni URLs
  de retour ;
- le prestataire Mobile Money réel ne peut pas être appelé sans URL ni clé API ;
- les webhooks de paiement rejetteront les requêtes faute de secret ;
- les retours de paiement ne pourront pas confirmer correctement les abonnements ;
- le portail Account utilisera une URL locale par défaut si ACCOUNT_WEB_URL manque ;
- la politique CORS peut retomber sur une valeur trop permissive ;
- la fonction de bootstrap Super Admin restera inutilisable tant que son secret manque.

Action obligatoire : configurer les secrets distants, redéployer les fonctions, puis
effectuer des tests bout en bout avec des événements de test Stripe/Orange Money et
un email reçu dans une vraie boîte de réception.

10. ERREURS UTILISATEUR ET OBSERVABILITÉ
======================================================================

[PASS PARTIEL] Application mobile
Un normaliseur transforme de nombreuses erreurs réseau, JWT, permission, stock,
doublon, impression et partage en messages compréhensibles. React Query journalise
les erreurs et les assainit avant affichage. Une table app_error_events et une vue
Super Admin existent pour le suivi.

[FAIL — P1] Risque d’erreurs techniques encore visibles
Plusieurs écrans mobiles affichent directement query.error.message ou
mutation.error.message. Le hook global React Query les assainit généralement, mais
cette protection dépend de la mutabilité de l’objet Error et n’est pas une garantie
à chaque chemin.

Les sites Account et public réutilisent encore directement des messages Supabase
dans plusieurs actions (connexion, devis, mot de passe, MFA, support et employé).
Un message interne peut donc encore atteindre l’utilisateur.

Action obligatoire : faire passer toutes les erreurs des trois sites web et tous les
chemins hors React Query par un normaliseur partagé, puis tester avec des erreurs
RLS, réseau, doublon et fonction RPC absente.

[RISQUE] Aucun service externe spécialisé de crash reporting n’a été détecté.
La table Supabase interne est utile, mais il faut vérifier qu’une erreur de connexion
à Supabase elle-même reste observable et qu’aucune donnée sensible n’est stockée.

[RISQUE P1 À CLARIFIER] Protection des colonnes financières
Le fichier todo.txt indique encore que le lot SQL de protection fine de champs
financiers sensibles est conservé dans un stash et non déployé. Les politiques RLS
existantes sont positives, mais cette note interne doit être fermée par un test
Admin/Employé prouvant qu’un employé non autorisé ne peut jamais lire le prix d’achat,
la marge ou d’autres champs financiers sensibles.

15. CONCLUSION
======================================================================

StockMaster V1 n’est pas un projet cassé : son socle technique compile, ses tests
unitaires passent et sa base distante est synchronisée. Mais un lancement réel ne
peut pas être déclaré sur la seule base de compilations locales. Les intégrations
serveur indispensables, les preuves RLS authentifiées, les binaires signés, les tests
sur appareils et les informations légales manquent encore.

Décision finale de cet audit : NO-GO.

Prochaine porte de validation : fermer les P0, obtenir une CI verte sur un commit de
release et fournir les résultats de recette des builds EAS preview Android et iOS.
